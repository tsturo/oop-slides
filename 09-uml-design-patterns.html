Custom exceptions let you create meaningful error types that describe exactly what went wrong in your specific application domain.

Recap: Lecture 06

Custom Exceptions: Domain Errors

  • Inherit from Exception or a specific built-in exception
  • Name them clearly: InsufficientFundsError, InvalidEmailError
  • Add custom attributes for extra context
  • Makes error handling expressive and precise
class InsufficientFundsError(Exception):
    def __init__(self, balance, amount):
        self.balance = balance
        self.amount = amount
        super().__init__(
            f"Need {amount}, have {balance}"
        )

SOLID: Interface Segregation

  • Don't force classes to implement methods they don't need
  • Split large interfaces into focused, cohesive ones
  • In Python: use multiple ABCs instead of one big ABC
  • Result: decoupled, easier to maintain code

    @abstractmethod

    @abstractmethod

        return "Printing..."

Quiz Time! (Lecture 08)

Which pattern ensures a class has only one instance?

A) Singleton

B) Factory Method

C) Observer

D) Strategy

Singleton restricts instantiation to one object. It overrides __new__ to return the same instance every time.

Recap: Lecture 08

Design Patterns: Singleton

  • Ensures a class has exactly one instance
  • Provides a global access point to that instance
  • Common uses: database connections, loggers, config objects
  • In Python: override __new__
class Singleton:
    _instance = None

    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
        return cls._instance

a = Singleton()
b = Singleton()
print(a is b)  # True

What is UML?

  • 📐 Unified Modeling Language — a standardized visual language for software design
  • 🎨 Not a programming language — a modeling language
  • 🤝 Provides a common vocabulary for developers, architects, and stakeholders
  • 📄 Used to visualize, specify, construct, and document software systems
UML helps you think about design before you write code.

Design Patterns

Quick recap before we dive deeper

Design Patterns: Recap

  • 📚 Reusable solutions to commonly occurring problems in software design
  • 🧱 Not finished code — a template for how to solve a problem
  • 👥 Shared vocabulary among developers: "Let's use a Factory here"
  • 🛠️ Introduced by the Gang of Four (GoF) in 1994
The GoF catalogued 23 design patterns in three categories.

The Three Categories

🏭 Creational

Object creation mechanisms

  • Singleton
  • Factory Method
  • Abstract Factory
  • Builder
  • Prototype

🗃️ Structural

Class/object composition

  • Adapter
  • Facade
  • Decorator
  • Proxy
  • Composite, Bridge, Flyweight

🔄 Behavioral

Object interaction & responsibility

Observer, Strategy, Iterator, Command, State, Template Method, ...

Creational Pattern

Factory Method

Define an interface for creating objects — let subclasses decide which class to instantiate

Factory Method: Problem

Imagine a logistics app that initially only handles truck transport.

  • 🚚 All your code is tightly coupled to the Truck class
  • 🚢 Now you need to add Ship transport — but Truck is hardcoded everywhere
  • 💥 Adding each new transport type requires changing existing code
This violates the Open-Closed Principle — we're modifying existing code to add new behavior.

Factory Method: Solution

  • 🔨 Define a factory method in the base class
  • 🔄 Subclasses override it to create specific products
  • 🟢 New transport? Just add a new subclass — no existing code changes

Factory Method: Code

from abc import ABC, abstractmethod

class Transport(ABC):
    @abstractmethod
    def deliver(self):
        pass

class Truck(Transport):
    def deliver(self):
        return "Delivering by land in a box"

class Ship(Transport):
    def deliver(self):
        return "Delivering by sea in a container"
class TransportFactory:
    @staticmethod
    def create_transport(transport_type: str) -> Transport:
        factories = {
            "truck": Truck,
            "ship": Ship,
        }
        return factories[transport_type]()
transport = TransportFactory.create_transport("ship")
print(transport.deliver())
# "Delivering by sea in a container"

Factory Method: Pros & Cons

🟢 Pros

  • Follows Open-Closed Principle
  • Loose coupling between creator and products
  • Easy to add new product types
  • Single Responsibility — creation logic in one place

🔴 Cons

  • Can lead to many subclasses
  • More complex than direct instantiation
  • Overkill for simple cases with few types

Structural Pattern

Facade

Provide a simplified interface to a complex subsystem

Facade: Problem

  • 📚 You're working with a complex library or framework
  • 🛠️ You need to initialize many objects, track dependencies, execute methods in the correct order
  • 💥 Your business logic becomes tightly coupled to implementation details of 3rd-party code
  • 😳 Code becomes hard to read and maintain
Without a Facade, client code must know all the internals of the subsystem.

Facade: Solution

  • 🗃️ Create a class that provides a simple, high-level interface
  • 📦 It wraps the complex subsystem and delegates calls internally
  • 🟢 Clients interact with the Facade — not the subsystem directly

Real-world: Phone Operator

When you call a store to place an order, the phone operator is your facade:

  • 📞 You tell them what you want
  • 🏭 They handle the warehouse (check stock)
  • 💳 They handle payment (charge your card)
  • 🚚 They handle delivery (schedule shipping)

You don't need to know how each department works internally.

Facade: Structure

Facade: Code

class VideoFile:
    def __init__(self, filename):
        self.filename = filename

class CodecFactory:
    def extract(self, file):
        return f"codec for {file.filename}"

class BitrateReader:
    def read(self, file, codec):
        return f"reading {file.filename}"

class AudioMixer:
    def fix(self, result):
        return f"fixing audio: {result}"
class VideoConverter:
    def convert(self, filename, format):
        file = VideoFile(filename)
        codec = CodecFactory().extract(file)
        result = BitrateReader().read(file, codec)
        result = AudioMixer().fix(result)
        return f"{filename} converted to {format}"
converter = VideoConverter()
print(converter.convert("funny_cats.ogg", "mp4"))
# "funny_cats.ogg converted to mp4"

Facade: Pros & Cons

🟢 Pros

  • Isolate complexity from client code
  • Promotes loose coupling
  • Makes subsystem easier to use
  • Can structure subsystem into layers

🔴 Cons

  • Can become a god object coupled to everything
  • May hide necessary complexity
  • Extra layer of indirection

Facade: When to Use

  • 🗃️ You need a limited, simple interface to a complex subsystem
  • 📂 You want to structure a subsystem into layers
  • 📚 You're wrapping a 3rd-party library and want to shield your code from its API changes
  • 👥 You want to provide a convenient default while still allowing advanced access

Behavioral Pattern

Iterator

Traverse a collection without exposing its internal structure

Iterator: Problem

  • 📦 Collections can have different structures: list, tree, stack, graph
  • 🔄 Each structure stores elements differently
  • 💥 Client code shouldn't need to know how elements are stored to iterate over them
  • 😳 Mixing traversal logic with business logic makes code hard to maintain
We need a way to access elements sequentially without exposing the underlying representation.

Iterator: Solution

  • 🔨 Extract traversal behavior into a separate iterator object
  • 🔭 In Python: implement __iter__ and __next__
  • 🟢 The collection provides an iterator — clients use it without knowing internals
Python has this built in! Every for loop uses the iterator protocol.

Iterator: Code

class NumberCollection:
    def __init__(self, start, end):
        self._start = start
        self._end = end

    def __iter__(self):
        self._current = self._start
        return self

    def __next__(self):
        if self._current >= self._end:
            raise StopIteration
        value = self._current
        self._current += 1
        return value
numbers = NumberCollection(1, 5)
for n in numbers:
    print(n)
# 1, 2, 3, 4
# Python generators — iterators made simple
def countdown(n):
    while n > 0:
        yield n
        n -= 1

for i in countdown(3):
    print(i)  # 3, 2, 1

Iterator & Python's for Loop

Python's for loop is syntactic sugar for the iterator protocol:

Under the hood

it = iter(collection)
while True:
    try:
        item = next(it)
    except StopIteration:
        break

What you write

for item in collection:
    process(item)
💡 Any object with __iter__ + __next__ works with for, list(), sum(), etc.

Dependency Injection: Recap

From SOLID's Dependency Inversion Principle:

  • 🔄 Inject dependencies instead of creating them inside classes
  • 🟢 Makes code testable and flexible
  • 🔧 Easy to swap implementations
class NotificationService:
    def __init__(self, sender):
        self._sender = sender

    def notify(self, msg):
        self._sender.send(msg)

sms = SMSSender()
svc = NotificationService(sms)
svc.notify("Hello!")

Anti-Patterns: What to Avoid

🔴 God Object

  • One class that knows too much or does too much
  • Violates SRP — many reasons to change
  • Hard to test, maintain, and extend
  • Example: a Manager class with 50 methods

🍝 Spaghetti Code

  • Code with no clear structure
  • Tangled dependencies, mixed concerns
  • Impossible to follow the flow
  • Often results from no planning or design patterns
Design patterns are the antidote to anti-patterns. They give your code structure and purpose.

Key Takeaways

  • 📐 UML — visual language for designing and documenting software systems
  • 📂 Class diagrams show structure: classes, attributes, methods, relationships
  • 🔄 Sequence diagrams show behavior: interactions over time
  • 🏭 Factory Method — delegate object creation to subclasses (creational)
  • 🗃️ Facade — simplified interface to a complex subsystem (structural)
  • 🔁 Iterator — traverse collections without exposing internals (behavioral)
Use patterns when they solve a real problem. Don't force them where they don't fit.
